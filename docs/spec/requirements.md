# Requirements Catalog

Derived from [vision.md](vision.md). Inception artifact.

- **Scope:** spans and traces only. Metrics appear only as an input
  (FR-011). Metrics and logs gating is deferred (FR-022, OTelFeature/poc#11,
  P2); the noisy demo is deferred (FR-017, OTelFeature/poc#23, P2).
- **Baseline:** `poc` @ `404d54d`, `otelfeature-instrument` @ `9dd4488`
  (v0.2.0), `otelfeature-java-extension` @ `f20c07c` (v0.3.1).
- **Priority:** High = the demo arc cannot be performed without it (backlog
  P0). Medium = a script line is false or a bracket stays empty without it
  (P1). Low = nice to have or post-talk (P2).
- **Status:** Open, In Progress, Implemented, Verified, Deferred, Rejected.
  Progress follows the use cases that list the requirement (AIUP; Simon,
  2026-10-16, OQ-12): Open = no linking use case is Implemented yet; In
  Progress = some are, others not; Implemented = every linking use case is
  Implemented or Tested; Verified = every one is Tested. So a requirement
  whose code is merged stays Open or In Progress until each use case it
  serves is complete. A use case is Implemented when its flows run on
  `main` (extensions not yet released, C-006), Tested when its test case
  passes in the end-to-end suite (NFR-015). Deferred and Rejected are set by
  hand, as is the status of a requirement no use case links. Which PRs
  implement what is in [traceability.md](traceability.md#implementation).
  Statuses as of 2026-10-16.
- Which issue implements which requirement is in
  [traceability.md](traceability.md). Issue refs are given here only where the
  requirement *is* the issue.

Roles used in the user stories:

- **Operator**: whoever manages the flags for a service (SRE, platform
  engineer, or the speaker on stage).
- **Speaker**: Simon or Juliano, performing the demo.
- **Adopter**: someone running the extensions or the demo after the talk.
- **Maintainer**: someone who develops the extensions or the demo stack.

Domain terms are defined in the [glossary](glossary.md).

## Functional Requirements

| ID | Title | User Story | Priority | Status |
|---|---|---|---|---|
| FR-001 | Boolean tracing kill switch | As an operator, I want a boolean flag `otelEnabled` that turns span creation off and on in every service at runtime, so that I can stop span ingest during an incident without a redeploy. Trace context keeps propagating while off (known limitation, UC-001 BR-006). | High | Verified |
| FR-002 | `OFF` variant of `telemetryLevel` | As an operator who already manages `telemetryLevel`, I want an `OFF` variant that behaves exactly like `otelEnabled=false`, so that I don't need a second flag for the kill switch. Both are kept (D2). | High | Verified |
| FR-003 | Suppress `INTERNAL` spans | As an operator, I want `telemetryLevel=IO` to drop `INTERNAL` spans and keep the trace tree connected, so that traces show only the I/O boundary. | High | Verified |
| FR-004 | One telemetry policy per decision | As a maintainer, I want every flag read collapsed into one `TelemetryPolicy` resolved once per decision point, so that each new flag costs one field and failure handling lives in one place. | High | In Progress |
| FR-005 | Evaluation context from semantic conventions | As an operator, I want flag targeting rules to see the span's resource, instrumentation scope and start attributes under their semconv names, nested by dot segment, with the trace id as `targetingKey`, so that I can write rules like `service.name == "weather" && url.path == "/health"`. On a leaf/prefix collision the namespace wins; extension-provided keys (resource, `span.kind`, `otel.scope.*`) win over a clashing start attribute; the `otelfeature.*` namespace is reserved and cannot be set by span attributes. | High | In Progress |
| FR-006 | Drop root spans by rule before creation | As an operator, I want a `recordSpan` targeting rule to drop matching root spans (for example health checks in one service) before they are created, so that the service doesn't pay CPU and memory for spans nobody reads. An incoming request span (`SERVER`/`CONSUMER`) with a remote parent counts as a root: dropping it drops the whole request in that service, and downstream services receive `sampled=0` (the trace ends at the caller). | High | Implemented |
| FR-007 | Drop leaf spans by instrumentation scope | As an operator, I want a `recordSpan` targeting rule on `otel.scope.name` to drop matching leaf spans (for example JDBC or psycopg spans in one service), so that a flooding instrumentation can be muted live. In Python a rule that reads only keys present on the tracer is decided once per tracer, so the muted scope costs nothing per span (OTelFeature/poc#12). | High | Implemented |
| FR-008 | Switchable Java enforcement point | As a maintainer, I want the Java extension to enforce decisions either in a sampler or in a span processor, selected by `OTELFEATURE_ENFORCEMENT` (default `processor`), so that both can be measured before one is chosen for the talk (OQ-1, pending OTelFeature/poc#27). | High | In Progress |
| FR-009 | Trace sample ratio as a number flag | As an operator, I want a `traceSampleRatio` number flag (0.0 to 1.0) that samples trace roots, with the same trace landing in the same bucket in every service, so that I can change sampling live and keep traces complete. Only trace roots evaluate the ratio; everything else is parent-based. Each language uses its own SDK's trace-id ratio formula, so Java and Python can disagree on a trace id at the same ratio; this is accepted (only the entry service decides), and cross-language consistency comes from a `fractional` rule on `targetingKey` (trace id). | High | Open |
| FR-010 | Services declare their own resource attributes | As an operator, I want each service to emit `service.name`, `service.namespace`, `service.version` and `deployment.environment.name` itself, with a production and a staging instance, so that rules can target an environment. | High | Open |
| FR-011 | Service error rate in the evaluation context | As an operator, I want the service's current HTTP server error rate, computed from its existing `http.server.request.duration` metric by an in-process delta reader, available as `otelfeature.http.server.error_rate` in the evaluation context, so that a rule can react to errors. Below `OTELFEATURE_ERROR_RATE_MIN_REQUESTS` (default 10) requests in an interval the key is omitted. | Medium | Open |
| FR-012 | Fault injection flag | As a speaker, I want a `weatherUpstreamFailure` number flag that makes that fraction of `/weather` requests fail, so that I can cause an incident on demand. | Medium | Implemented |
| FR-013 | Error-driven sampling rule | As an operator, I want a targeting rule that sets `traceSampleRatio` to 1.0 for a service whose error rate is above 5%, and returns to the ratio the other rules give once the rate drops (on stage `weather`'s 0.5 from `03a-weather-boost`), so that sampling goes up exactly where and when it is needed. | Medium | Open |
| FR-014 | Extension decisions are not written onto spans | As an operator, I want the extensions to add no attributes of their own to spans: no `feature_flag.*`, no `otelfeature.sample_ratio`, no tracestate `ot=th`. Recording flag evaluations is the OpenFeature OpenTelemetry hook's job; for the extension's own evaluations it is opt-in only (`OTELFEATURE_OPENFEATURE_TRACING_HOOK=true`, never default, evaluation exceptions excluded), so that I can debug a rule without paying an event per span in normal operation. | Medium | Open |
| FR-015 | Application flag evaluations visible in traces | As an operator, I want the applications' own flag evaluations (such as `weatherUpstreamFailure`) recorded on spans using the `feature_flag` semantic conventions, so that a trace shows which flag caused the failure. | Medium | Open |
| FR-016 | Measured savings | As a speaker, I want a repeatable before/after measurement of CPU, memory, spans/s and export bytes per service, so that the numbers on the slide are real. | Medium | Open |
| FR-017 | Noisy demo workload | As a speaker, I want the demo to produce health-check traffic, a chatty DB path and a higher request rate, so that the drop is obvious. Deferred: not needed for the talk, the wall of spans comes from OTel Demo footage (C-007). Demo 2 must work on the stack's normal traffic (OQ-5). The health-check part is split out as OTelFeature/poc#38 (P0, PR OTelFeature/poc#40). | Low | Deferred |
| FR-018 | Offline stage mode | As a speaker, I want the stack to run with no network, external APIs stubbed, so that the demo doesn't depend on venue Wi-Fi. | High | Open |
| FR-019 | Stage controls | As a speaker, I want named flag presets, a one-command flip per script beat and a reset, so that each demo starts from a known state. | High | Open |
| FR-020 | Public, runnable demo repo | As an adopter, I want to clone the demo repo and run `make start` with only Docker installed, so that I can try what I saw in the talk. | Medium | Open |
| FR-021 | Env-var tier documentation | As an adopter, I want to know which `OTEL_*` env vars can become live flags and which cannot, so that I know what OTelFeature can and cannot replace. | Low | Open |
| FR-022 | Per-signal kill switches | As an operator, I want `signalsEnabled` to turn traces, metrics and logs off separately. Out of talk scope (spans only). | Low | Deferred |
| FR-023 | Per-span drop flag `recordSpan` | As an operator, I want a boolean flag `recordSpan` (default `true`, key override `OTELFEATURE_RECORD_SPAN_FLAG_NAME`), evaluated per span against the semconv context, so that I can drop exactly the spans a targeting rule matches while `otelEnabled` and `telemetryLevel` stay global switches. Precedence: hard floors (C-011) > `otelEnabled`/`telemetryLevel=OFF` > `recordSpan`; `recordSpan=true` never re-enables anything. Fails open: a missing flag, a provider error or a non-boolean value means record. | High | Implemented |
| FR-024 | Honour `OTEL_METRICS_EXPORTER=none` | As an adopter, I want both extensions to treat `OTEL_METRICS_EXPORTER=none` the way the SDK does: no metrics SDK is installed, so the error-rate reader (FR-011) is not registered, `otelfeature.http.server.error_rate` is absent from the context and error-rate rules never match (logged once at startup), so that switching metrics off doesn't switch them back on through the extension. Only an exact `none` counts (case and surrounding whitespace ignored); `none` mixed with other values logs a warning and keeps exporting. | Medium | Open |
| FR-025 | Honour `OTEL_TRACES_EXPORTER=none` | As an adopter, I want `OTEL_TRACES_EXPORTER=none` to mean "export nothing" in both extensions, as it does in the SDK: no span exporter is configured, while the tracer, the flag policy and context propagation keep working, so that downstream services still receive `traceparent`. This is not a kill switch: spans are still started and the recording CPU cost remains (use `otelEnabled`, FR-001, to stop that). Java gets this from SDK autoconfigure; Python implements it. Same parsing as FR-024. | Low | Implemented |
| FR-026 | Cross-service request path | As a speaker, I want the load generator to also call a `geocode` endpoint that calls `weather` over HTTP, besides the direct `POST /geocode` and `POST /weather` calls, so that the demo has traces spanning both services: on that path `geocode` is the entry point and `weather` follows the parent's decision (UC-004 BR-003), while the direct `POST /weather` traffic keeps `weather` the entry point of its own traces. The cross-service path carries a small share of `geocode`'s requests, so a `weather` incident keeps `geocode`'s own error rate under the 5% threshold at stage load (UC-005 A7). Decided by Simon, 2026-10-16 (OTelFeature/poc#59). | Medium | Open |
| FR-027 | Stage stack from extension git refs | As a speaker, I want to start the demo stack (`make start`, `make start-staging`, `make prepare-offline`) with both extensions built from git refs (`EXT_REF`, or `OTELFEATURE_INSTRUMENT_REF` / `OTELFEATURE_EXTENSION_REF`), so that I can rehearse and show the real demo before the extensions are released. Without a ref the stack uses the pinned released versions (C-006). Each image records which extension source it was built from, and `make start` prints it, so a git build is never mistaken for the pinned one. Building from a ref needs the network; afterwards the stack runs offline as usual (FR-018). Second exception to C-006, next to the e2e suite (C-013). OTelFeature/poc#61. | High | In Progress |

## Non-Functional Requirements

| ID | Title | Requirement | Category | Priority | Status |
|---|---|---|---|---|---|
| NFR-001 | Fail open | If the provider is not ready or unreachable, the flag is missing, has the wrong type, an unknown variant or an invalid value, every policy field resolves to the value derived from the startup env vars (stock OTel behaviour). For `traceSampleRatio` a negative value, NaN, infinity or a non-number is invalid; a value above 1.0 is clamped to 1.0, not invalid (UC-004 A1). The failure is logged once per state change, not per span. No exception reaches the application. | Availability | High | In Progress |
| NFR-002 | No network on the span hot path | A flag decision for a span performs no network I/O. Flags are evaluated by the flagd in-process resolver from a ruleset synced over gRPC (port 8015). | Performance | High | Implemented |
| NFR-003 | Static-flag fast path | When every flag the policy reads resolves with reason `STATIC`, a span decision is one volatile read: no flag evaluation, no hook chain, no evaluation-context allocation. Verified by an allocation test or benchmark in each extension. | Performance | High | In Progress |
| NFR-004 | Flag change propagation | A flag change saved to `flagd.json` affects new spans within 2 s in both services, without a restart. flagd reloads a file only when its mtime strictly increases, so every rewrite must leave a newer mtime ([entity model](entity_model.md#flag-file-reload)). | Performance | High | In Progress |
| NFR-005 | Per-span decision cost is measured | The cost of one targeted (non-static) span decision, including context build, is measured once per language (JMH / pytest-benchmark) and reported in the extension README and the measurement table, so claimed savings are net of the evaluation. The acceptable upper bound is not set yet (OQ-3). | Performance | Medium | In Progress |
| NFR-006 | Footprint | The extensions add no new metric, span attribute, span event or tracestate entry to the OTLP export (FR-014); with the opt-in tracing hook switched on, the hook's `feature_flag.evaluation` events are the only addition. The extra in-process metric reader (FR-011) does not change what reaches the collector. Memory held by the extension is bounded (Java suppressed-span registry: 10,000 entries). The resident-memory overhead per service is reported by the measurement harness. | Performance | High | Open (memory report: OTelFeature/poc#27) |
| NFR-007 | One decision per span | A span's fate is decided once, at start, and not re-asked at end. Within one trace, parent-based sampling stays consistent; `fractional` buckets use the trace id so every service puts a trace in the same bucket. | Maintainability | High | In Progress |
| NFR-008 | Non-breaking drop-in | Installing either extension with flags at their defaults produces the same spans as the stock SDK/agent (plus nothing). | Usability | High | In Progress |
| NFR-009 | Isolation from the application's OpenFeature | The Java extension uses an isolated `OpenFeatureAPI` and never replaces the application's global provider. The Python launcher lets the application take over with `OTELFEATURE_FLAG_PROVIDER=none`. | Portability | High | Verified |
| NFR-010 | Startup never blocks on flagd | Service startup does not wait for flagd. Until the provider is ready, flags resolve to defaults (NFR-001). | Availability | High | Implemented |
| NFR-011 | Reproducible measurements | Two runs of the measurement harness with the same preset agree within ±10% per metric. | Maintainability | Medium | Open |
| NFR-012 | Rehearsal repeatability | Each demo run-through, started from the reset command, works three times in a row. | Usability | High | Open |
| NFR-013 | Error rate is sampling-independent | The error rate fed into the context (FR-011) is identical whether spans are sampled at 1.0 or 0.0. | Maintainability | Medium | Open |
| NFR-014 | Error-rate lag and minimum | The error rate in the context lags the traffic by one to two collection intervals (`OTELFEATURE_ERROR_RATE_INTERVAL`, default 10 s). A service that handles fewer than `OTELFEATURE_ERROR_RATE_MIN_REQUESTS` (default 10) requests per interval never gets a rate, even in a total outage. Both are documented in the extension READMEs. | Maintainability | Medium | Open |
| NFR-015 | Every demo beat is verified automatically, before merge | The talk script's demo beats (TC-001, TC-002, TC-004, TC-005, TC-006 and the env-var hard floors) run as an end-to-end suite against the real stack (Docker Compose with `compose.e2e.yaml`) in GitHub Actions on every pull request, on `main` and nightly, in both Java enforcement modes. Assertions read every exported span, so absence is checked exactly; waits are poll-until with timeouts, never fixed sleeps. The suite passes three runs in a row without flakes and is green before any extension or `poc` stack is merged (C-013). TC-003 (measurement) and TC-007 (fresh clone) are not part of it. | Maintainability | Medium | Open |
| NFR-016 | Reproducible toolchain, local = CI | Each repo defines its toolchain in `ci/Dockerfile`: base image pinned by tag and digest, dependencies preinstalled in a layer keyed on the lock files. `make test` (and `make e2e` in `poc`, `make shell` everywhere) runs inside that image; GitHub Actions builds and uses the same image (buildx, GHA layer cache) instead of `setup-python`/`setup-java`. Dependabot watches the Dockerfiles. | Maintainability | Medium | In Progress |

## Constraints

| ID | Title | Constraint | Category | Priority | Status |
|---|---|---|---|---|---|
| C-001 | Spans and traces only | The talk controls spans and traces. Metrics are only an input to span decisions. No metric or log gating is built for the talk. | Business | High | Verified |
| C-002 | flagd in-process provider | Flags are served by flagd (v0.17) and evaluated in-process (gRPC sync on 8015) in both extensions. OFREP polling was rejected (OTelFeature/otelfeature-java-extension#9). | Technical | High | Verified |
| C-003 | Only start-time attributes | Rules can only use attributes known when the span starts. `http.route` and `http.response.status_code` are not available then (D6), so rules target `url.path`. | Technical | High | In Progress |
| C-004 | Sampler drop takes the subtree | A sampler `DROP` removes the span and its whole subtree and propagates `sampled=0` downstream. The Java sampler therefore only drops root spans (including incoming request spans with a remote parent) and leaf spans (DB client spans). A span that propagates mid-trace is suppressed by the processor in both modes, and so is a rule the sampler cannot see (for example `otel.scope.name`: a `Sampler` is not told the scope). Known edge, documented, not fixed: with a non-parent-based sampler (for example `OTEL_TRACES_SAMPLER=always_on`), children of a dropped root are sampled as orphans. | Technical | High | Implemented |
| C-005 | Python HTTP metric opt-in | The FastAPI/ASGI instrumentation emits `http.server.request.duration` with `error.type` only with `OTEL_SEMCONV_STABILITY_OPT_IN=http`; otherwise the old `http.server.duration`. The extension documents the opt-in but does not set it (it renames metrics and attributes users see). Without it, errors are counted as `http.status_code >= 500`; with `http/dup` only the stable metric counts. | Technical | Medium | Open |
| C-006 | Released extension versions | The demo stack consumes released versions of both extensions (`OTELFEATURE_EXTENSION_VERSION` build arg, Python package pin). Final measurements and the control loop need releases that contain the features. Exceptions: the stage stack when started with an explicit extension git ref (FR-027, UC-008 BR-008), and the end-to-end suite builds from extension git refs until those releases exist (C-013). | Technical | High | Open |
| C-007 | OTel Demo as footage only | The opening hook uses recorded OTel Demo footage (D1). No live OTel Demo on stage. | Operational | Medium | Open |
| C-008 | Fallback video | Each demo has a recorded fallback in case the live run fails. | Operational | Low | Open |
| C-009 | External API usage policy | Nominatim allows about 1 request/s per source IP. Higher request rates require the stubbed APIs (FR-018). | Regulatory | High | Open |
| C-010 | Collector is not a decision point | Nothing is built in the collector (D4). The script says the collector *could* read the same flags. | Business | Medium | Open |
| C-011 | Env-var hard floors | `OTEL_SDK_DISABLED=true` and `OTEL_TRACES_SAMPLER=always_off` cannot be overridden by any flag or by a sampled parent. Flags only reduce telemetry; they never enable what an env var switched off. In Java, autoconfigure still calls the extension's customizer when the SDK is disabled; it then installs nothing, not even the flagd connection. `parentbased_always_off` keeps its standard meaning: no trace starts sampled locally, sampled parents are followed. | Technical | High | In Progress |
| C-012 | Stock sampler names only (Python) | Python's plain SDK tracer provider never loaded custom samplers. The extension parses `OTEL_TRACES_SAMPLER` like the SDK; an unknown name (including `jaeger_remote`) falls back to a ratio of 1.0 with a warning. | Technical | Medium | Open |
| C-013 | E2E runs against extension git refs until released | The end-to-end suite (NFR-015) is the safety net before merging, so it can run against unreleased extension code: Python installed with `git+https://…@ref`, the Java JAR built from the ref in a Docker stage (it reuses the extension's `ci/Dockerfile` once OTelFeature/otelfeature-java-extension#35 lands). Both extension chains are merged, so the default ref is each extension's `main` until releases exist; then the defaults switch back to pinned released versions (C-006). Merge order: extension stacks bottom-up (done), then releases, then the `poc` version bump, then the `poc` stack (see [traceability.md](traceability.md#merge-order)). | Technical | Medium | Open |
| C-014 | Docker-only development in WSL, LF line endings | Tests, builds and the stack run inside WSL (Ubuntu, WSL2) with Docker as the only host tool; every other tool runs from a Docker image (NFR-016) and is never installed on the host. Scripts and Dockerfiles use LF line endings, enforced by `.gitattributes`. | Operational | Medium | In Progress |
